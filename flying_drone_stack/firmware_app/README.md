# Firmware App — Onboard SE(3) / INDI Controller (no_std Rust)

## 1. Overview

`firmware_app/` is a separate Rust crate that compiles the onboard controller into the
Crazyflie STM32 firmware binary as an *out-of-tree controller*.  It runs at
**500 Hz inside the firmware's stabilizer task**, receiving the Kalman EKF state and
the position setpoint sent from the laptop over radio, and outputting thrust + torques
directly to the motor mixer.

Two controllers are implemented, switched by one constant (`CONTROLLER_MODE` in
`src/lib.rs`, see §"Controller mode" in `firmware_app/CLAUDE.md`): **Mode 0 = SE(3)
geometric** (Lee et al. 2010, default) and **Mode 1 = Full INDI** (Tal & Karaman 2020,
requires RPM deck). Both are the *onboard deployment target* of the controllers
validated offboard in `src/controller/` (`GeometricController` / `IndiController`).
Gains and math are identical; the only differences are the platform constraints:
`no_std`, `f32` arithmetic, and FFI types generated by `bindgen` from the Crazyflie C
headers.

**Lecture slides requirements addressed:**

| Requirement | Where |
|-------------|-------|
| `#![no_std]` — switch from `std` to `core` | `src/lib.rs:30` |
| `f32` arithmetic throughout | all controller math |
| `bindgen` FFI bindings from `stabilizer_types.h` | `build.rs` + `wrapper.h` |
| Controller logic linked into C firmware binary | `Kbuild` staticlib link |

**Reference**: Lee, T., Leok, M., McClamroch, N.H. (2010). Geometric tracking control of
a quadrotor UAV on SE(3). *49th IEEE CDC*, pp. 5420–5425.

## 2. Architecture

```
Laptop (20 Hz, radio CRTP)              Crazyflie STM32F405 (500 Hz)
┌─────────────────────────────┐         ┌────────────────────────────────────┐
│ Trajectory generator        │         │ Sensor drivers (IMU, flow)         │
│ SLAM / MEKF / safety layer  │─setpt──▶│ Kalman EKF (state estimator)       │
│ CSV logging (src/bin/main)  │         │                                    │
└─────────────────────────────┘         │ ← controllerOutOfTree() ←          │
                                        │   (firmware_app/src/lib.rs, 500 Hz)│
                                        │                                    │
                                        │ Motor mixing + PWM drivers         │
                                        └────────────────────────────────────┘
```

The laptop stack continues to handle trajectory generation, MEKF estimation, SLAM, and
safety — all at 20 Hz over radio.  The firmware app handles the **inner control loop**
(position + attitude) at the full 500 Hz stabilizer rate, using the drone's own Kalman
EKF state and raw IMU data.

### Control flow inside the firmware

```
controllerOutOfTree(control, setpoint, sensors, state, tick)
         │
         ├─ Extract pos, vel, quaternion → rotation matrix R
         ├─ Extract gyro [deg/s] → omega [rad/s]
         ├─ Extract setpoint: position pd, velocity vd, accel ad, yaw_d
         │
         ├─ geometric_step(pos, vel, R, omega, pd, vd, ad, yaw_d, dt, &CTRL)
         │      ├─ Position P+I controller → desired force F_d
         │      ├─ desired_rot(F_d, yaw_d) → R_d
         │      ├─ Rotation error eR = ½(Rd^T R − R^T Rd)∨
         │      └─ Torque τ = −KR·eR − Kω·ω + ω×Jω
         │
         └─ Write thrust [N] + torque [Nm] to control_s (controlModeForceTorque)
```

## 3. Crate Structure

```
firmware_app/
├── Cargo.toml         # no_std staticlib; deps: panic-halt, libm; build-dep: bindgen
├── Cargo.lock
├── app-config         # Kconfig: APP_ENABLE=y, CONTROLLER_OOT=y, STACKSIZE=1024
├── Kbuild             # Calls cargo build --release, copies .a as app.o
├── Makefile           # Wraps crazyflie-firmware oot.mk; exports CRAZYFLIE_BASE
├── build.rs           # Runs bindgen on wrapper.h → $OUT_DIR/bindings.rs
├── wrapper.h          # #include stabilizer_types.h + controller.h
├── .cargo/config.toml # default target = thumbv7em-none-eabihf
└── src/
    └── lib.rs         # no_std controller: Vec3, Mat3, geometric_step, entry points
```

### Why a separate crate?

The firmware app cannot share code with the main `flying_drone_stack` library:
- The main library uses `std` (tokio, cflib, jpeg-decoder…)
- The firmware app must be `no_std` for the Cortex-M4 target
- It produces a `staticlib` (`.a`), not a `rlib`

Conceptually it is the **onboard deployment of the controller component** — the same
SE(3) math, gains, and structure, but packaged for the STM32 instead of the laptop.

## 4. Key Data Types (from bindgen)

`build.rs` generates Rust FFI bindings for the following types from `stabilizer_types.h`:

| C type | Purpose | Used in |
|--------|---------|---------|
| `control_s` | Output: thrust + torque (union) | write to `control` |
| `setpoint_s` | Input: desired pos/vel/acc/yaw from laptop | read `setpoint` |
| `sensorData_s` | Input: raw IMU (gyro `Axis3f`) | read gyro → omega |
| `state_s` | Input: Kalman EKF state (pos, vel, quat) | read current state |
| `quaternion_s` | Nested in `state_s.attitudeQuaternion` | extract qw, qx, qy, qz |
| `control_mode_e` | Enum: `controlModeForceTorque = 1` | set output mode |

### Quaternion convention

The Crazyflie firmware uses **Hamilton, scalar-last** storage:
- `state.attitudeQuaternion.{x, y, z, w}` → `qx, qy, qz, qw`
- In `q0..q3` naming: `q0=qx`, `q1=qy`, `q2=qz`, `q3=qw` (scalar)
- Bindgen adds two anonymous union levels: `.__bindgen_anon_1.__bindgen_anon_1.q3` for `qw`

### Output layout (`controlModeForceTorque`)

```
control_s union offset  0 (f32): thrustSi  [N]
                 offset  4 (f32): torque[0] = torqueX [Nm]
                 offset  8 (f32): torque[1] = torqueY [Nm]
                 offset 12 (f32): torque[2] = torqueZ [Nm]
control_s.controlMode = controlModeForceTorque (= 1)
```

Written via raw pointer arithmetic to avoid deeply nested bindgen anonymous struct names
while keeping the layout explicit: `*union_ptr.add(N) = value`.

## 5. no_std Math

`f32::sqrt()` is not a compiler intrinsic in stable no_std Rust.  All transcendental
functions use the `libm` crate:

| Function | Used for |
|----------|---------|
| `libm::sqrtf` | `Vec3::norm()` |
| `libm::cosf`, `libm::sinf` | `desired_rot()` (desired heading vector) |

## 6. Controller Parameters

Gains are identical to the offboard `GeometricController::default()` in `src/controller/mod.rs`,
validated on real hardware (Mar 2026, hover + circle + figure-8):

| Constant | Value | Physical meaning |
|----------|-------|-----------------|
| `KP_X/Y` | 7.5   | Position proportional XY [m/s²/m] |
| `KP_Z`   | 26.0  | Position proportional Z (stiff altitude hold) |
| `KV_X/Y` | 9.0   | Position derivative XY [m/s²/(m/s)] |
| `KV_Z`   | 14.0  | Position derivative Z |
| `KI_P`   | 0.0   | Position integral (disabled — anti-windup included but gain=0) |
| `KI_LIMIT`| 2.0  | Anti-windup clamp [m/s²·s] |
| `KR_X/Y` | 0.007 | Attitude proportional [Nm/rad] |
| `KR_Z`   | 0.008 | Attitude proportional (yaw) |
| `KW_X/Y` | 0.00115 | Attitude derivative [Nm/(rad/s)] |
| `KW_Z`   | 0.002 | Attitude derivative (yaw) |
| `MASS`   | 0.027 kg | Crazyflie 2.1 + Flow Deck v2 |
| `JXX/JYY/JZZ` | 16.571 / 16.656 / 29.262 µN·m² | Inertia (Crazyflie official System ID) |

Arming threshold: controller outputs zero until `setpoint.position.z > 0.05 m` (prevents
motors from spinning during the HLC takeoff ramp before the spline trajectory starts).

## 8. INDI Controller (3-Mode System)

The firmware implements three controllers selectable via `CONTROLLER_MODE` in `src/lib.rs`.
All three are fully implemented and compile-ready — switch by changing the constant and reflashing.

```rust
const CONTROLLER_MODE: u8 = 0;   // 0 = Geometric (default, validated)
                                  // 1 = Attitude INDI  (gyro-only, no RPM deck needed)
                                  // 2 = Full INDI      (RPM deck required — see prerequisites)
```

### Mode 0 — SE(3) Geometric (active default)
Model-based `−KR·eR − KW·eω + ω×(J·ω)` torque. Unchanged from the course baseline.
All existing Rust and Python flight scripts work with this mode.

### Mode 1 — Attitude INDI (gyro-only)
Replaces the KR/KW torque law with an incremental law:
```
ω̇_filt ≈ IIR((ω − ω_prev) / dt,  fc = FC_GYRO_HZ)
Δτ = J · (α_des − ω̇_filt)
τ_new = τ_prev + Δτ
```
- No RPM deck needed. Uses `act_dyn` first-order motor model to estimate `τ_prev`.
- G2 yaw coupling correction (Smeur 2016) implemented via `du_prev_z` state.
- **To activate:** set `CONTROLLER_MODE = 1`, `make cload`, run `cargo run --release --bin indi_hover`.
- All existing flight scripts work unchanged (controller switch is firmware-internal).

### Mode 2 — Full INDI (RPM-based)
Replaces the modelled `τ_prev` with the actual torque computed from per-motor RPM²:
```
τ_current = G(Ω) · [Ω₁², Ω₂², Ω₃², Ω₄²]    ← measured via RPM deck
```
The math is fully implemented (`compute_tau_from_rpm`, `full_indi_torque`).
The call site passes `[0.0; 4]` pending the 4-line RPM sensor read.

**Prerequisites before setting `CONTROLLER_MODE = 2`:**
1. RPM deck physically fitted to the drone
2. `KT` identified on bench (thrust-stand sweep; replace the placeholder `3.16e-10`)
3. Replace `[0.0; 4]` at the Mode 2 call site with `[sens.motor.m1² … m4²]`

### Key constants (Mode 1 & 2)

| Constant | Value | Meaning |
|----------|-------|---------|
| `FC_GYRO_HZ` | 60.0 Hz | Butterworth cutoff for angular acceleration filter |
| `ACT_DYN` | 0.1 | First-order motor model coefficient; `τ_motor = dt*(1−α)/α` |
| `G2` | 0.0 | Yaw gyroscopic coupling; 0 = standard INDI (safe default) |
| `KT` | 3.16e-10 | Thrust coefficient [N/RPM²] — **placeholder, bench-identify before Mode 2** |

### Simulation equivalence
`tests/test_firmware_indi_equiv.rs` (5/5 passing) verifies the firmware INDI law
produces identical torques to `src/controller/indi.rs` at matching gains.
`tests/test_indi_vs_geometric.rs` (5/5 passing) validates sim behaviour including
a phase-stability analysis documenting the noise-free vs hardware difference.

## 9. Connections to Other Modules

| Direction | Component | What is exchanged |
|-----------|-----------|------------------|
| Uses math from | `src/controller/` | Same SE(3) algorithm and gains (two independent copies, both validated) |
| Receives setpoints from | `src/bin/main.rs` | Position + yaw via CRTP `setpoint_position` (20 Hz); or full-state (pos+vel+acc+quat+ω) via CRTP type 6 from spline test binaries (25 Hz) |

| Reads sensors from | Crazyflie IMU | `sensorData_s.gyro` at 500 Hz |
| Writes to | Crazyflie motor mixer | `control_s`: thrustSi [N] + torque[3] [Nm] |

## 10. Common Pitfalls

**`f32::sqrt()` not in no_std**: The `sqrt` method on `f32` requires the floating-point
runtime in `std`.  Use `libm::sqrtf(x)` instead.

**Double `__bindgen_anon_1` nesting**: The `quaternion_s` type has an outer anonymous
union and an inner anonymous struct.  Access scalar `qw` as:
`state.attitudeQuaternion.__bindgen_anon_1.__bindgen_anon_1.q3`.

**Gyro units**: `sensors.gyro` is in **deg/s**.  Convert to rad/s before using in the
controller: `omega = gyro * (π / 180)`.

**Setpoint yaw units**: `setpoint.attitude.yaw` is in **degrees** (HL commander
convention).  Convert to rad: `yaw_d = sp.attitude.yaw * deg2rad`.

**SD card logging not available**: The Crazyflie used in this course does not have a
uSD deck.  In-flight data is logged via the radio CSV path in `src/bin/main.rs`
(equivalent coverage, different transport).
