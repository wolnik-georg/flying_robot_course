Findings from reading the code:
- **"Thrust factor" is a cap.** With the calibration values the law reaches 0.1098·(0.2/0.1236)² = 0.2875 N at full command, so a cap of 0.2758 N acts only in the top 4 % of the command range. The gradient of any cost with respect to `fmax` is zero in normal flight. There is no continuous thrust-gain input in any copy (the law constants 0.1098 and 0.2·0.618 are literals; `kt` scales only the lateral components).
- **RPM delay and state delay are integers** (indexed gather); not differentiable. RPM delay matters only for S1 and S3.
- **β relevance per controller:** thrust cap and motor lag act in all 8; RPM delay only in S1 / S3 (S0, S2, FBL do not read the RPM, `frsim/episode.py` feeds RPM only for the tree); downwash scale and plume amplitude act only on flights with a top vehicle (A1, A8; not on solo circle / figure 8 / oval). So 4 of the 8 controllers have at most 4 identifiable β, and on the solo scenarios only 2 (thrust cap, lag).
- **`T.K` caches CPU tensors by `id()`** (`s0_torch.py:17-26`): a leaf β tensor on the CPU that is re-created each iteration could return a stale cached tensor; CUDA tensors skip the cache. To be handled when β becomes an input.
- The S0–S3 copies use the rounded plant inertia (relative error up to 0.03 %); the FBL copy and `frsim` use the exact one.
- Reference data of the copies come from `diff/build_bank.py` (A1 / A4 / A8 grid cells built through `plant_core` / `core.py`), not from the vendored `frsim` scenario code; `diff/traj.py` has its own circle / figure-8 families for training episodes (not the flown trajectories).
- The copies model the firmware plant; the equivalence gate and the S0 correction note show that the *RMS error* agrees to ≤ 0.5 %, while the *trajectories* separate by mm to cm in strong-tilt cells (A4 line, first A8 cell). J_sysId compares trajectories, so the tolerance of the forward check has to be stated per signal (Stage 2.5).
