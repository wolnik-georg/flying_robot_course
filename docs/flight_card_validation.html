2026-09-12, part 1 — H0 partition

done — inconclusive, real finding

ctrl_mode=2 (attitude INDI alone) crashed sharply: peak roll 119.7°, z dropped 0.017m, onset timed exactly to the geometric→INDI handover tick (t=6.58s). For completeness, ctrl_mode=1 (position INDI alone) was flown too and crashed differently: peak roll 179.3°, z to -1.457m (real impact), onset gradual, starting ~t=11.2s — the position-loop/attitude-bandwidth cascade mismatch already on file, not a new mechanism. An rpm_m1 dropout at t=19.2s in that flight is a symptom of the tumble, not its cause (well after the t=11.2s divergence onset) — flagged so it isn't chased as a red herring.

Full INDI (ctrl_mode=3) was then re-flown as a sanity check and passed as expected — stable hover/figure8, just the already-known attitude oscillation, no new issue.

Conclusion: the H0 partition does not cleanly localize the shake — both sub-loops are individually worse alone than the combined system, which is itself the useful negative result. The ctrl_mode=1 gradual divergence has an explanation on file; the ctrl_mode=2 sharp, handover-timed divergence does not yet have a second concrete root cause the way the stage-2d notch crash does — left open rather than overclaimed.

The stage 2d notch crash was root-caused offline the same day, separately: the 2026-07-29 fix that hoisted alpha_meas/alpha_ref notch-filter warm-up out of the mode-gated branch missed a third chain, tau_current's own Butterworth pre-filter (bw_tau_x/y/z), which only started updating at the same tick as the controller handover — a cold-start transient, same class as the original bug. Fixed in firmware_app/src/lib.rs (commit bc7190c), verified compiling clean and behavior-preserving at defaults on both platforms — not yet reflashed/flown, needs a real notch_en=1 test next session.

2026-09-12, part 2 — first 2-drone flight

done — clean flight achieved, 6 bugs fixed

cf_second enabled for the first time — a standard CF2.1 (RPM deck + mocap marker + uSD deck), not brushless yet, to validate the multi-drone infrastructure cheaply before committing to a reflash. Layout runs Y-axis separation (checked for no code dependency, more geofence margin than X). Running formation_flight.py for real surfaced six genuine, durable bugs — all fixed, none flight-specific workarounds:

  1. Missing pos_gains selection for ctrl_mode=0 — the exact 2026-09-09 root cause, fixed in simple_flight.py back then, never ported here. Ported the same GEOMETRIC_POS_GAINS override.
  2. Mid-air controller-identity-switch risk — the ramp config assumed the target was always our own OOT controller; switching controller identity itself (e.g. to stock Lee) mid-air is the exact mechanism behind the worst 2026-09-09 crashes. Fixed: when the target isn't OOT, ramp and fly the whole flight on that config, no switch.
  3. No hover support — the script always called uploadTrajectory() unconditionally; added a hover_mode branch mirroring simple_flight.py.
  4. Arming gated behind a --brushless flag, not passed on the mixed-fleet flight — CF21BL silently never armed. Arming is a generic safety gate, not brushless-specific (confirmed in supervisor.c); fixed by arming unconditionally and removing the flag.
  5. LOG_DIR hardcoded to a dev-machine path — crashed the entire flight with an uncaught exception on flightcontrol1 (different machine), leaving both drones hovering with no autonomous recovery. Fixed by importing flight.py and reusing its already-correct LOGS_DIR, and wrapping all log writes in try/except so logging can never again block landing/disarming.
  6. Landing collision for vertical (stacked) formations — a broadcast land gives every drone the same duration regardless of height, so two drones sharing XY collapsed to near-zero separation on descent (confirmed: one drone at 166.6° roll, a real tumble). Fixed by porting run_formation.py's existing pattern: spread onto a 0.35m circle in XY, then land each drone individually at a matched descent rate scaled to its own live height.

First fully clean flight (stock Lee, both drones, all fixes applied): landed correctly, logged correctly, no exceptions. cf231_active (lower, in the downwash) showed roll std 17.9°/peak 38.2° vs cf_second (upper) at 0.75°/peak 5.8° — stock Lee has zero interaction-force awareness, so it just reacts reactively. a_res was exactly 0 for both, as expected (that computation lives inside our own controller, which never ran).

Then tried our OOT geometric controller on both drones — both crashed. cf_second oscillated almost the entire flight (roll to 179.5°); cf231_active crashed within ~2s of leaving the ground, coinciding with a real a_res_z spike of 8.1 m/s² — consistent with being hit by the drone thrashing overhead. Both drones inspected, no damage.

Root cause, corrected twice on the way to the real answer. First suspected kr_geo/kw_geo as brushless-only and untested on standard — wrong, checked via git: those values are bit-identical to the compile-time constant flying clean on standard back on 2026-07-02. The real, larger bug: the shared all: firmware config (fc_bw, clamp_en, res_fc/res_clamp, notch settings) has drifted brushless-only for two months, and standard silently inherited all of it the moment it was re-enabled. Bigger still, found later the same day: apply()'s broadcast also carries indi_gains.mass/kt1-4 from the shared block, which was silently wiping cf_second's per-robot mass/kt override on every single apply() call, including the very first one before takeoff — so it almost certainly flew on brushless's thrust model (~2.8× off on kt), not its own. This explains cf_second (standard)'s own instability, not cf231_active (brushless)'s crash directly — brushless's config was never touched by this bug, since it's the platform the shared config is tuned against; its crash reads as collateral damage from the standard drone thrashing directly above it in the stacked formation, not a separate fault of its own. Generalized load_per_robot_overrides() to re-push any per-robot stabilizer/indi_gains/pos_gains key after every broadcast (commit fdfc640) — fixes both the controller/ctrl_mode case and this bigger mass/kt case for good.

Decision, session closed on this: next session switches cf_second to brushless (removes this whole failure mode rather than re-tuning standard from scratch — yaml's per-robot override block is already marked TEMPORARY with a delete-me note), then validates uSD logging on both cards (never yet exercised in a real 2-drone flight — today's dataset was radio only). Only then does real C.1 data collection begin. Full account: docs/lab_sessions/2026-09-12.md.
