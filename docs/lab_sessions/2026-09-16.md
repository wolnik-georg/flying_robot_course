## 1. What happened, in order

**First real 2-drone full-INDI attempt — crashed.** `cf231_active`'s geometric-only override
(quietly in place since 2026-09-14) was removed to finally exercise "step 1: Full INDI, 2
drones, A8" from the Next Flight Card gate for the first time. It crashed: `cf231_active`
destabilizes first, `cf_second` ~0.3–0.4s later; separation only *grows* through the failure,
ruling out a collision.

**Investigation ruled out, in order:** `--passes 2` (the most-flown value in project history);
a bad Poly4D upload (coefficients checked, sane); the geometric→full-INDI mid-air switch
itself (already proven safe single-drone via `flight.py`).

**Root cause found: the optical RPM deck reports exactly zero for 2 of 4 motors throughout
real flight**, reproducibly, invisible on a secured bench test. This is a real hardware
defect in the deck-based RPM path, not a config or gain problem.

**Separately, `simple_flight.py` still had the mid-flight `usec.reset` bug** already fixed in
`flight.py`/`run_formation.py` on 2026-09-15 — never ported to this script. Fixed.

**Switched to DShot** (`indi_gains.rpm_source=1`) per the existing plan
(`flying_drone_stack/docs/dshot_rpm_source_plan.md`). An early pair of DShot flights looked
clean but turned out to be **logging the deck's own (broken) variables regardless of
`rpm_source`** — a second, independent bug: the radio log topic and the control-path param
are separate switches. Fixed by pointing the log at DShot's own variables.

**With that fixed: four consecutive flights (2 hover, 2 figure8) on DShot came back
completely clean** — zero RPM dropouts across all 4 motors, every log, roll/pitch bounded to
the known baseline oscillation only.

**Final confirmation:** physically removed the deck's reflective prop markers (deck itself
stays mounted — needed for mocap). Hover and figure8 both still flew clean, proving DShot has
zero dependency on the optical sensor.

**Decision: DShot is now the standing RPM source for `cf231_active`.**

This resolves RPM as a *candidate* cause of the original 2-drone A8 crash but does **not**
resolve the crash itself — the 2-drone full-INDI gate has still never been flown clean. It
remains the next actionable step, now with a working RPM source. Also still open, separately:
the 2026-09-09 audit fix (N1, pins `alpha_ref` to the INDI gain pair during the geometric
ramp) — see §2f below, now closed as a non-driver.

**Evening desk-time: worked through the full Briesewitz-comparison list, one item at a time.**
Following the DShot resolution, went through every item enumerated in `docs/22` §2e as a
runtime toggle, each flown through the same full-INDI hover on `cf231_active` (single-drone,
on DShot):

- **N1** (2026-09-09 audit fix, `n1_fix`) — off vs on through a real geometric-ramp→full-INDI
  handover: indistinguishable. Left at default (`1`).
- **Item #5** (`dt` resolution, `dt_usec`, `usecTimestamp()` vs 1ms-quantised tick):
  indistinguishable. Left ON anyway — strictly more precise, no worse.
- **Item #2/torque** (torque residual conditioning, `tau_clamp=0.03`): indistinguishable.
  Reverted to `0.0`.
- **Item #3** (per-axis yaw filtering, `fc_bw_yaw=10.0`, matching NA-INDI's own reference
  value): **made it measurably worse** — roll std 1.08→1.98° (~1.8×), pitch std 0.64→1.86°
  (~2.6×) vs the immediately-preceding baseline flights, despite yaw's own filtered signal
  being *less* noisy (32.7 vs 55.6 std) — a phase-lag-on-yaw's-own-loop-coupling-into-
  roll/pitch effect, not a noise problem. Reverted immediately to `0.0`.

Items #1 (`a_res` conditioning) and #4/filter-rate (`fc_bw` retune) were already closed from
the 2026-09-11 session (applied / tried-and-reverted respectively); the gyro-source item was
already ruled out 2026-09-10.

**Conclusion: the Briesewitz-comparison approach is now exhausted — 7/7 items tested or
addressed.** Six null/neutral, one (per-axis yaw filtering) confirmed harmful and reverted.
None explains the attitude oscillation. The pattern across both filtering failures (`fc_bw`
retune 09-11, `fc_bw_yaw` today) — more filtering trades noise for phase lag, and this loop's
own dynamics don't tolerate it — points back to the native `kr`/`kw`/`pos_gains` tuning line
(`docs/22` §2h, "stage 2 item (e)") as the more promising remaining lead, not further filter
comparison work.
