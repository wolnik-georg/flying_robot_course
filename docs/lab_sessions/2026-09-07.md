## 1. What happened, in order

1. **Flashed firmware** (`make cload`) with the three previously-unflown residual-learning
   fixes (sign fix, `a_res` gating, `rnn.en=0`). Build was clean.
2. **IndexError probe** (`debug/connect_probe.py`) — first attempt hung 30s and crashed
   uncaught (server wasn't up yet); second attempt, run *after* the server was confirmed up,
   passed **10/10**. Per the existing debug checklist's own decision rule, this is not the
   deep race bug — just "wait for the server," resolved.
3. **First `simple_flight.py` hover** — its first-ever real hardware flight. Ran under
   `ctrl_mode=3` (full INDI) by accident (that was `crazyflies.yaml`'s existing default).
   Reported "issues with INDI gains."
4. **Switched to geometric for now**: `ctrl_mode: 3 -> 0` in `crazyflies.yaml`.
5. **Second hover, geometric** — analysis of the CSV (after correcting for a misleading
   post-landing EKF dead-reckoning artifact in the raw z column) showed a real, growing
   oscillation: roll std ~21° in the clean hover window, dominant frequency ~1.1 Hz.
6. **Root-cause investigation**: diffed the current firmware/config against the frozen
   `finalized-version-for-INDI-project` branch. Found `clamp_en: 11` (tilt clamp **off**) —
   a setting left over from the Phase-4 inverted-loop maneuver test, never reverted when the
   brushless config block was parked on 2026-07-29. Two other hypotheses were checked and
   downgraded: an always-on residual-network eval (turned out to already short-circuit to
   zero work when unloaded/no peers) and the runtime frame-convention switch (`g_indi_frame_conv`,
   inert under the default `omega_src=0` for Mode E/B).
7. **Fixed `clamp_en: 11 -> 15`** (all four clamps restored) — a runtime param, no reflash
   needed. Pushed.
8. **Re-flew hover under both controllers post-fix.** Result: **the clamp fix did not resolve
   the oscillation.** Both still grow in amplitude, but as two genuinely different phenomena:

   | | Geometric | INDI |
   |---|---|---|
   | Dominant frequency | 0.56 Hz | 3.92 Hz |
   | Roll std, first half → second half of hover | 9.2° → 20.4° | 15.3° → 19.8° |

9. **First diagnosis (WRONG mechanism, corrected below)**: initially assumed geometric and
   INDI were sharing one `kr`/`kw` attitude-gain pair (`kr=2400/kw=170`, tuned and locked via
   INDI figure-8 tracking), and that this shared pair explained geometric's 0.56 Hz mode.
10. **Firmware change (built on the wrong assumption)**: added a separate `kr_geo`/`kw_geo`/
    `kr_z_geo`/`kw_z_geo` gain pair, auto-selected by `ctrl_mode` in `controller_step`, wired
    into the `alpha_ref` computation. Built clean, committed, pushed.
11. **Caught the real bug**: geometric's torque (`mode & 2 == 0` branch) was never computing
    from `kr_xy`/`kw_xy` at all — it used **separate compile-time constants**
    `KR_X/KR_Y/KR_Z = 0.010`, `KW_X/KW_Y = 0.00110`, `KW_Z = 0.00138`, tuned per
    `firmware_app/CLAUDE.md`'s own gains table for the **standard CF2.1 (27g, Flow Deck)** —
    not this 41g brushless platform. Step 10's `kr_geo`/`kw_geo` split changed a value
    (`alpha_ref`) that only feeds INDI's incremental term; it had **zero effect on geometric's
    actual behaviour**. Both geometric flights analysed in step 8 were flying the *standard*
    platform's fixed gains the whole time, on a substantially heavier drone — a much more
    plausible real explanation for a mass/inertia-driven growing oscillation than the original
    "shared aggressive INDI gains" theory, which was factually wrong about the mechanism.
12. **Fixed properly**: the geometric branch now reads the same `kr_xy`/`kw_xy`/`kr_z`/`kw_z`
    locals as the rest of the function (which already resolve to `kr_geo`/`kw_geo` when
    `mode==0`), instead of the compile-time constants. Builds clean.
13. **⚠ Caught a safety bug before it was ever flashed**: `kr_geo=1200/kw_geo=85` (seeded in
    step 10) is wrong by **~5 orders of magnitude**. Geometric computes
    `torque = -kr_geo*eR - kw_geo*eOmega` **directly in Nm**; INDI's `kr`/`kw` feed
    `alpha_ref` (an *angular acceleration*, `[1/s^2]`) which only becomes torque later,
    multiplied by inertia `J` (~24×10⁻⁶). A value in INDI's range, used directly as
    torque gain, would command roughly `1/J` (~40000×) too much torque — very likely a
    violent crash on arming, not a mild oscillation. **Corrected to `kr_geo=0.010,
    kw_geo=0.00110, kr_z_geo=0.010, kw_z_geo=0.00138`** — the original geometric
    constants, already flight-proven all session (as the compile-time values, pre-fix) not
    to crash, just mildly oscillate. This is the correct, safe starting point for a real
    tuning ladder. **Neither the wrong nor the corrected value has been flashed/flown yet.**
14. **Operator correction, and the real finding**: hover, figure8, oval, circle, **and the
    inverted loop** all flew fine historically (before this session) with a known, **bounded**
    (not growing) attitude oscillation — under `clamp_en=11`. That ruled out "INDI was never
    validated for hover" as an explanation. Re-ran a **complete** parameter diff (every value,
    not just the filter toggles) between the parked/frozen brushless block and today's config:
    **`clamp_en` was the only thing that differed** — `kr`, `kw`, `kr_z`, `kw_z`, `mass`,
    `kt1-4`, `fc_bw`, `filt_order`, `filt_tau`, `j_scale`, `ff_free`, `notch_en`, `tau_xy_max`,
    `tau_z_max`, `tilt_max_deg`, `thrust_max`, `kp_xy`, `kp_z`, `kv_xy`, `kv_z` are all
    byte-identical. **This means step 7's `clamp_en: 11 -> 15` "fix" earlier today was the
    wrong direction** — restoring the tilt clamp is the most likely actual cause of the new
    *growing* oscillation, not a fix for it. Plausible mechanism: the clamp is a saturation
    nonlinearity; if commanded tilt sits near the 30° boundary, repeated engage/disengage
    injects a discontinuous correction into `Rd` that a loop tuned (and only ever flown) with
    the clamp off was never subjected to. **Reverted `clamp_en` back to 11**, matching the
    frozen/parked, actually-flight-proven state. Also confirmed RPM data in today's INDI flight
    is real and live (not stuck/zero) — ruling that out as a cause too.
15. INDI's 3.92 Hz mode from step 8 needs re-checking now that `clamp_en` is back to 11 — it
    may have been partly or wholly a symptom of the clamp change too, not a re-emergence of the
    old pre-existing shake investigation as first assumed in step 9.
