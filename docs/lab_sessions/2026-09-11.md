## 1. What happened, in order

1. **Found and fixed a real trajectory-export bug before any flying.** Circle/figure8 at
   kt=0.05 showed a violent ±53° roll oscillation at the very start of the trajectory (not the
   controller — confirmed by evaluating the exported CSV's own polynomial independent of any
   flight log). Root cause: `export_poly4d.rs`'s wind-up/wind-down ramp searched for the
   shortest dynamically-feasible duration starting from 0.65s; that duration let a degree-7
   Hermite polynomial ring (peak acceleration ~7 m/s², sign-reversing). Fixed by raising the
   search floor to 1.2s (`flying_robot_course` `976352d`), re-exported and re-verified the
   kt=0.05 CSVs (`crazyswarm2` `bfa4db9`). Confirmed fixed in flight — residual wobble judged
   acceptable, floor can be nudged higher later if it ever matters again. Full writeup:
   [`project_trajectory_ramp_ringing_2026-09-11`](../../.claude — see memory) — the mechanism,
   the on-path `--rest-to-rest` alternative that was re-examined and confirmed still worse even
   with more QP iterations, and why the two-part (periodic core + wind-up ramp) design is
   necessary, not over-engineered.
2. **Stage 1 (geo hover/circle/figure8 + INDI hover, restored config): all PASS**, kt=0.05 used
   throughout (operator confirmed this substitution is fine; card literally specifies kt=0.1/
   kt=0.008 but the speed difference doesn't matter for what's being validated).
3. **Stage 2a** (`res_fc=80`, `res_clamp=10`): PASS, INDI hover clean.
4. **Stage 2b** (`filt_prewarp=1`, `filt_dt_us=1000`, `fc_bw=206` as a deliberate no-op):
   confirmed genuinely a no-op — hover matched 2a almost exactly, circle/figure8 shake
   unchanged in magnitude. Validates the sample-rate fix is implemented correctly.
5. **Stage 2c** (`fc_bw=100`, first real tuning step): made everything worse — hover regressed
   from PASS to FAIL (peak 17.3°, growing), circle peak roll nearly tripled (27.5°→69.2°).
   Reverted to `fc_bw=206`.
6. **Stage 2d** (`notch_en=1`, `notch_f0=6.9`, `notch_bw=3.0`): **CRASHED.** Stable hover to
   t=6.4s, then roll/pitch diverged to 88.7°/66.6° and altitude collapsed (1.07m→0.64m) within
   0.7s — a real impact. This was the very first actual flight test of the notch (a 2026-07-29
   note flagged a suspected cold-start-transient fix as never sanity-checked; that fix did NOT
   resolve whatever makes the notch unsafe here). Reverted `notch_en` to 0 immediately.
   **Root cause NOT understood — do not re-enable without offline analysis first.**
7. **Drone inspected after the crash — no damage found**, session resumed same day.
8. **Stage 2e (the shake-band test), four attempts:**
   - Attempt 1: `kr/kw=987/109` (ω_n 5.0Hz) alone, `pos_gains` left at 64/5 — aborted early
     (manual kill, ~2s in), operator reported it starting to diverge. Surfaced a real,
     previously-untested failure mode: `pos_gains` were tuned assuming the *original* 7.8Hz
     attitude bandwidth, so slowing `kr`/`kw` alone shrinks the cascade's inner/outer timescale
     separation.
   - Sim attempt to de-risk this coupling **failed to produce a usable answer**: a plain
     stationary hover at the failed hardware gains was perfectly flat in sim (roll std
     0.0014°). Conclusion: the sim's idealized actuators and near-perfect position estimate
     don't reproduce this failure mode at all — sim cannot be trusted for this question.
   - Attempt 2: `kr/kw=987/109` **with matched `pos_gains`** (`kp_xy=26`, `kv_xy=3.2`, scaled to
     hold the same ζ_pos=0.3125 the locked point uses) — hover PASSED cleanly, best of the day
     (std 0.99°). But figure8's shake was essentially unchanged from the stiff baseline (peak
     roll 17.6° vs 17.7°). Confirms the coupling mechanism was real (uncoordinated diverges,
     coordinated doesn't), but the shake-band question itself stayed open.
   - Operator's own counter-evidence and supervisor input both pointed back to gain magnitude:
     stock firmware defaults (`kr=100`/`kw=30`, ω_n=1.59Hz) are independently known stable.
     Reconciled with attempt 2's flat result via this project's own documented precedent for a
     *sharp* stability boundary, not smooth degradation (the `kw=130` "real floor, not
     noise-band scatter" finding from July) — 5.0Hz likely still sits on the unstable side.
   - **EKF-phase-lag theory raised and explicitly rejected**: INDI flies cleanly on the other,
     non-brushless drones using the identical EKF/mocap pipeline, so the estimator can't be the
     differentiator. Live brushless-specific candidates if revisited: actuator/motor dynamics
     (measured τ≈44ms brushless vs 71ms upgraded, a real physical difference) or the RPM/DShot
     feedback path — not the estimator.
   - Attempt 3: bisected to `kr/kw=483/76` (ω_n 3.5Hz) with the same matched-scaling formula
     (`kp_xy=13`, `kv_xy=2.2`) — hover peak roll dropped to 11.4° (real progress vs 17.6-17.7°),
     but `z` overshot to 1.195m and drifted (mean 1.091) — `pos_gains` now too weak to hold
     position. Still FAIL.
   - Attempt 4: kept `kr/kw=483/76`, switched `pos_gains` to **geometric's own already
     flight-validated point** (`kp_xy=40`, `kv_xy=8`, `kp_z=30`, `kv_z=10`, ζ_pos=0.632) instead
     of extrapolating the INDI-locked ratio further — valid because INDI's outer position loop
     is the same code path as geometric's. Position holding fixed completely (z tight, no
     drift), attitude peak dropped further (6.7° vs 11.4°) — but hover picked up a small new
     growing trend it hadn't shown at any higher-gain config (std 1.80→2.75). Still FAIL.
   - **Ended the session reverted to `kr=2400`/`kw=170` + `pos_gains` 64/5/48/7** — the last
     unambiguously clean, flight-proven state — rather than leaving the config mid-experiment.
9. Second brushless drone (CF21BL #2) being prepared in parallel for tomorrow's multi-drone
