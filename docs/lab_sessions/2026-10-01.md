# Lab Session — 2026-10-01

## 1. What happened, in order

1. **A5 mocap-boundary crash**, first attempt — bottom drone lost tracking near the X-axis room
   boundary. Fixed with `--height 0.5`, `--rotate 90` (lay the translating motion along the room's
   long Y axis instead of the short X axis), and a permanent default-radius reduction
   (0.75m → 0.40m, matching the fix A2 already had — the room's X/Y asymmetry was documented in
   memory since 2026-09-02 but not checked before flying A5 for the first time). 3 clean A5
   flights followed.
2. **A6 and C4 flown at their extreme-gated parameters** — both crashed repeatedly (A6: 4 crashes
   in 5 attempts, real attitude tumbles 105-163° roll, consistent onset at the scenario's
   close-pass/reversal moment; C4: crashed too). A5 flew clean in between A6 attempts, ruling out
   a global stuck-state explanation — confirmed genuine control-margin failures at 8-10cm
   separation, not a software bug. **Decision: A6/C4 dropped from the active 2-drone
   data-collection target** (deliberate future-day decision to revisit at gentler parameters, not
   queued).
3. With A6/C4 out of scope, every scenario in the active 2-drone set (A1, A2, A3, A4, A5, A7, A8,
   C5) had multiple real C.1 flights banked — **C.1 data collection effectively complete.**
4. **C.2 retrain executed for real** (first time, not just desk-prepped) on a 26-flight bank
   (22 base + 3×A5 + 1×A6): combined R²=0.944 (up from 0.936), 81.7% reduction vs predict-zero.
   Per-scenario LOO on all 4 new folds: OK. **Gate PASSED** — Checklist G became a live option.
5. **`rnn.en=0` sanity flight (Checklist D)** hit a real bug: `upload_residual_weights.py` crashed
   with `ValueError: cannot convert float NaN to integer` reading back `rnn.ready` right after
   upload. Root-caused as a client-side read-timing race, not a firmware issue. Workaround used in
   the moment: verify via the `rnn.pred_z` log variable instead.
6. **First `rnn.en=1` real-control attempt (Checklist G)**: flew A1 twice. First worked (no
   tumble). Second crashed with the same signature later identified as the liftoff tumble (see
   below) — unrelated to `rnn`. Post-flight uSD analysis of the working flight found
   `rnn_pred_x/y/z` and `rnn_clamped` **exactly 0.0 for all 5002 samples** — the weights were
   never actually loaded into the firmware buffer, despite `rnn.en`/`rnn.ready` param readbacks
   looking clean. **Second, more serious upload-path bug found**: a clean readback is not proof
   the upload worked. Checklist G did not actually validate anything this attempt.
7. **Operator's own observation, preserved per explicit instruction**: on liftoff, with
   `ENABLE_Z_INTEGRAL=true`, the drone shoots up aggressively above its commanded height before
   correcting within a few seconds to a very low steady-state error. Flagged as a possible
   mocap-ceiling risk and a possible link to the day's repeat-crash pattern. Log pulling continued
   first, per operator's instruction, before analysis.
8. **uSD log pulling/merging completed** for the day's two batches (A5×3, A6×1, C4×1 working
   attempt, A1×2 working attempts — one `rnn.en=0`, one `rnn.en=1`). All crashed attempts produced
   0-byte uSD logs (established pattern, not a mystery in itself).
9. **Z-integral overshoot quantified and the straightforward "it causes the crashes" hypothesis
   refuted**: overshoot was largest (+15.8cm) on the A1 flight that worked, smallest/absent
   (+1.3cm, -2.0cm) on the two that crashed — inverse correlation, not supporting correlation.
   The real common factor across A1 and A6 crashes: a genuine attitude tumble ~0.65-0.75s after
   leaving the ground, independent of scenario, tight across 3/3 A1 tumbles.
10. **Correlate search across all 10 of the day's radio CSVs** (5×A1, 5×A6) via Cursor,
    independently validated — confirmed the 0.65-0.75s tumble timing is real and tight; ruled out
    `vbat` sag, `thrust` command shape, and flight order as discriminators; confirmed mocap
    occlusion is genuinely unobservable in this pipeline (no visibility channel logged anywhere);
    confirmed A6's tumbles are a separate mid-shuttle close-pass mechanism, not the same thing as
    A1's liftoff-specific tumble. No root cause found — real bottleneck identified: no telemetry
    survives a crash (0-byte uSD), so the one channel that could catch a motor-side asymmetry at
    the tumble's onset is missing exactly where it's needed.
11. **Upload script fixed** (desk work, after lab closed): both the NaN crash and the silent
    weight-load failure closed via a post-upload verification gate requiring both `rnn.ready==1`
    and `rnn.n==len(weights)` before reporting success or honoring `--enable`. Independently
    validated against the actual diff, compiles clean. Committed.
12. **Reread of code found the Z-integral already has anti-windup and resets to 0 every tick
    while grounded** — the "stale pre-loaded integral" sub-hypothesis looked structurally
    unlikely from static code alone.
13. **SIL damping/trade-off study, two rounds, both independently reproduced by re-running the
    actual scripts (not just trusting reports):**
    - `kv_z` sweep (4-18 at `ki_z=16`): current staged `kv_z=7` already near-optimal.
    - `ki_z` trade-off sweep (0-20, overshoot cost vs disturbance-rejection benefit): current
      staged `ki_z=16` already near the knee of the curve.
    - **Across every combination tested, SIL never exceeded ~22mm overshoot** — 7x smaller than
      the real 15.8cm seen on hardware. Strong signal the SIL model is missing something, not
      that an untested gain value explains the gap.
14. **Strategic clarification surfaced**: per `docs/07`'s own C.3 table, Strategy 0/1/2 (geometric
    baseline / pure INDI / NS2 residual) all share the `controller=6` code path — today's tumble
    is therefore a risk to the whole compared set, not an NS2-only problem. Separately, "Strategy
    1: Pure INDI" in the compared set is `controller=6, ctrl_mode=3` (already gate-passed on A8)
    — **not** Omar's separate C/Rust port (`controller=9`/`10`), which stays parked regardless.
15. **Omar's reference position-loop gains pulled for comparison**
    (`Kpos_P=7.0, Kpos_D=4.0, Kpos_I=0.0` — confirmed structurally equivalent control law to ours).
    Translated to damping terms: his is ωn≈2.65 rad/s, ζ≈0.76 (slower, more damped) vs ours
    ωn≈6.93 rad/s, ζ≈0.50. Caveat: the `kv_z` sweep already covered his damping ratio at our
    bandwidth and found no improvement, so this comparison tests his *combination* (lower
    bandwidth + his damping), not a knob already ruled out.
16. **Two-part follow-up sent to Cursor, pending as of session close**: (A) decode raw/uncropped
