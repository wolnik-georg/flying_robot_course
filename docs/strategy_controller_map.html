Strategy → Controller Map

Which firmware stabilizer.controller number implements which of the thesis's seven comparison strategies — written down once, precisely, so the controller=7 ↔ NA-INDI mix-up doesn't happen again.

The confusion, stated plainly

controller=7 is a faithful, numerically-verified port of Cobo-Briesewitz's own controller_lee.c — and that file's algorithm is called NA-INDI. It is tempting, and wrong, to conclude controller=7 therefore is NA-INDI.

Their file's use_nn flag — the part that makes it NA-INDI instead of plain INDI — is off in every configuration either project has flown, and controller=7 was ported with it left out. So controller=7, as it exists today, runs their plain INDI.

Correction, 2026-09-16: a real, trained network for this path DOES exist — nn.c in their firmware repo, generated from a real .pth model, with genuine calibration ranges (not placeholders). It solves a different problem than this thesis compares (their own single-vehicle payload residual, not inter-vehicle downwash) — see the controller=8 row below.

The resolution

controller=7 is a second implementation of Strategy 1 (Pure INDI) — legitimately citable, since the authors' own paper treats INDI as one of its four baseline methods (Lee / INDI / LINDI / NA-INDI), not a mislabelling of Strategy 4.

Real NA-INDI (Strategy 4) needs use_nn enabled and a trained residual model in their convention, wired into that same module — tracked as a future controller=8. 2026-09-16: control-law logic written, isolated, and compiles clean -- their real trained weights (not a placeholder) extracted and embedded, the full force+torque wiring ported line-for-line. Not yet wired into a firmware controller slot, and not yet numerically verified against the reference's own compiled C. Do not fly.

01One source file, three algorithms

Cobo-Briesewitz's controller_lee.c — one file, switched by two flags

indi = true  ·  use_nn = false

INDI

RPM feedback only. No learned residual.

indi = false  ·  use_nn = true

LINDI

Learned residual only. No RPM feedback at runtime.

indi = true  ·  use_nn = true

NA-INDI

Network predicts the bulk; INDI corrects only the leftover.

Our port (controller=7) carries all three code paths but hardcodes use_nn=0 — so only the left branch is live. Reaching the right branch (real NA-INDI, Strategy 4 / future controller=8) means enabling use_nn and supplying a trained model; the middle branch (LINDI) is not used by any strategy in this comparison.

03Definitions, for whenever this reads unclear again

INDI

Incremental Nonlinear Dynamic Inversion. Reacts to a measured residual, via rotor-speed (RPM) feedback. No learning, no prior model of the disturbance.

LINDI

A network replaces INDI's residual estimate entirely. No RPM measurement needed at runtime — the paper's actual headline claim (sensor elimination). Not used by any strategy in this comparison.

NA-INDI

Both together: the network predicts the bulk of the residual, and INDI's RPM feedback corrects only what the network got wrong. This is Strategy 4 — and it needs a trained network to mean anything.
