Goal: find and fix why `usd.runTag` / `usd.logging` sets sent through CS2 never reach the drones, so S0 round 0 can be flown with valid uSD logs.
Rules as always: facts from files and tool output only; "not stated" otherwise; nothing here is a measurement unless a file is named.
Earlier handover (18 Nov): `docs/HANDOVER_USD_LOGGING_LOST_2026-11-18.md`. Gate steps: `experiments/diffcotune/lab/USD_GATE_LAB_STEPS.md`.

## 1. The problem in one paragraph
Every flight script starts uSD logging by CS2 `allcfs.setParam('usd.runTag', tag)` then `allcfs.setParam('usd.logging', 1)` (broadcast). Since the reflash with `fbl_v2b_candidate.bin` (18 Nov) this never starts logging: no uSD file for any flight on 18 Nov or 20 Nov. The decks, cards, card config and image are fine: the same drones write ~880 kB files when `usd.logging` is set over cflib (radio, CS2 stopped). So the break is on the CS2 runtime-set path: the drone's `usd.runTag` stays at its old value (777, left by a cflib test) after CS2 reports success for a set to 888 / 999.

## 4. Open hypotheses (none confirmed)
H1 server never receives/handles the parameter event (ROS side: `/parameter_events` subscription filter `event.node == "/crazyflie_server"`, executor, ...). H2 server forwards but the firmware ignores it (fbl_v2b image, `PARAM_UINT32 runTag` / `PARAM_UINT8 logging` handling, param write rate/ordering). H3 type/declaration issue (uint32 declared as int64 ROS param). H4 yaml/log-block interaction (`usd_status` topic is new; fails on 18 Nov before it existed, so it is not the only cause). H5 the old 7 May server binary is incompatible with something in the new image although yaml params apply fine at connect (connect-time path and runtime path differ).
