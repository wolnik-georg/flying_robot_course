NS2 loop timing: inline today, parallel task as the option

Supervisor's question (2026-10-17): should NS2 run in its own loop and hand its result to the control loop through a queue? What the repositories show, how the two designs differ, and what the parallel one needs.

What I found. I could not find a parallel loop with a queue for the network in any repository I have: our firmware, the IMRC firmware fork, NA-INDI and its firmware, the Neural-Swarm reference, crazyswarm2. In all of them the network is evaluated inside the controller call. The Neural-Swarm papers say controller, Kalman filter and network run on the STM32.

What it would give us. The control loop never waits for the network: no timing hiccup every 20 ms, and more neighbours do not slow the motor update. The price is that the NS2 value is about 1 to 3 ms older when used.

For two drones the inline version is fine. The parallel one matters once each drone has two or three neighbours.

What the supervisor may have in mind: the Crazyflie firmware does run heavy or slow work in separate FreeRTOS tasks that talk through queues (app task, parameter task, radio tasks), and neighbour positions already arrive that way. Ask for the exact repository or file.

Today: inline one task does everything

One stabilizer task runs every millisecond. The controller step runs every second tick. On every tenth controller step the network runs inside it, and the motor command for that step goes out later.

Same code and same timing in all four strategies (S0 to S3): the network is evaluated everywhere and used only when rnn.en = 1, so the comparison between strategies is fair.

Parallel design control path never waits

A second task, with lower priority than the stabilizer, takes a snapshot of position, velocity and neighbours, runs the network and writes the answer into a queue of length one that overwrites. The controller only peeks at the last value and carries on.

The 20 ms hold dominates the value's age in both designs, and the downwash changes over about 0.1 s, so the extra 1 to 3 ms should not matter. The delay of the motor command should matter more for INDI, which is sensitive to delay in our earlier tests. I have not measured an effect of the 0.53 ms in flight.

What the parallel version needs

Code
  • One FreeRTOS task for NS2 with its own static stack, priority below the stabilizer.
  • A length-one queue with overwrite; the controller peeks with zero wait.
  • A consistent snapshot of position, velocity and neighbours, taken in the task under a short critical section.
  • An age stamp on the value and a fallback to zero when it is stale.
  • Reset on re-arm; host and simulation builds without FreeRTOS keep the inline path.
Checks
  • Bench: rnn.us_max and loop-rate supervisor with 1, 2 and 3 injected neighbours.
  • Byte-identical outputs against the inline build (host replay) with the hold set equal.
  • Closed-loop simulation and one hover flight before any study flight.
  • Log the value's age so the delay can be read from the flight data.
Risks
  • The task can be starved when the stabilizer and radio tasks are busy; the age check covers it.
  • Timing becomes non-deterministic; the inline version is easier to reproduce.
  • New code on the flight path right before the study. The controller tree is validated as it is.

Recommendation and the question to ask

Keep inline for the two-drone study (526 µs, 26 % of the slot, no problem seen in flights). Measure the timing with two and three injected neighbours before the three-vehicle phase, and build the parallel task only if the controller slot gets tight or if the 0.5 ms hiccup shows up as an effect on INDI.

Ask: which repository or file did you mean, with the network in a separate loop? Is the goal the control timing, the scaling with neighbours, or both? Do you want it for the two-drone study or only for the three-vehicle phase?
